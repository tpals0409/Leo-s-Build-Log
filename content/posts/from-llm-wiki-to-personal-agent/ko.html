시작은 LLM Wiki였습니다. Andrej Karpathy의 LLM Wiki 개념을 보고, 제 프로젝트 경험과 의사결정도 AI가 근거를 찾아 활용할 수 있는 지식으로 정리해 보고 싶었습니다.

프로젝트를 설명하려면 사용한 기술뿐 아니라 왜 선택했는지, 제가 맡은 일은 무엇인지, 어떤 문제를 겪었는지도 필요합니다. 이런 맥락을 기록으로 남겨 두면 다음 작업에서 다시 활용할 수 있겠다고 생각했어요.

이 과정에서 사용한 도구가 Hermes Agent입니다. 언어 모델에 파일 조회나 명령 실행 같은 도구를 연결해, 대화뿐 아니라 실제 작업을 수행할 수 있게 하는 AI 에이전트 도구입니다. 저는 Hermes를 기반으로 개인 에이전트를 구성하고 ‘루나’라는 이름을 붙였습니다. 별도의 모델을 학습시킨 것은 아닙니다. 기존 모델이 제 자료와 작업 규칙을 참고하도록 환경을 구성한 것입니다.

지금은 Telegram에서 루나와 대화하며 자료를 찾고, 지원서를 정리하고, 블로그를 작성합니다. 하지만 시작부터 지금의 모습을 모두 설계했던 것은 아닙니다. LLM Wiki로 시작한 시도가 어떻게 개인 에이전트를 운영하는 일로 이어졌는지 돌아보려 합니다.

대화 속 설명을, 다시 사용할 수 있는 기록으로

제가 정리하려던 것은 단순한 프로젝트 목록이 아니었습니다. 같은 프로젝트도 어떤 질문을 받느냐에 따라 필요한 내용이 달랐습니다. 아키텍처를 설명할 때와 협업 경험을 이야기할 때, 장애 대응 과정을 돌아볼 때 꺼내야 할 기록은 서로 다르니까요.

‘어떤 서비스를 만들었다’는 요약만으로는 충분하지 않았습니다. 결정의 이유와 제 역할, 그 설명을 뒷받침하는 원문까지 찾아갈 수 있어야 했습니다.

이를 위해 경험 원문과 위키 요약을 분리했습니다. 원문은 설명의 출처로 보존하고, 위키에는 사람이 읽고 검토하기 좋은 형태로 내용을 정리했습니다. 요약이 잘못되었을 때도 원문으로 돌아갈 수 있도록요.

Hermes는 이 자료를 읽고 작업하는 쪽을 맡았습니다. 지식을 보관하는 공간과 그 지식을 활용하는 에이전트가 연결되면서, 기록은 보관용 자료에서 실제 요청을 처리할 때 참고하는 맥락이 되었습니다.

이름을 붙인 뒤에도, 기준은 따로 만들어야 했습니다

에이전트에 ‘루나’라는 이름을 붙였다고 저를 이해하게 되는 것은 아닙니다. 이름보다 중요한 것은 무엇을 참고하고, 어떤 기준으로 일을 처리하도록 할지였습니다.

지원서 작성을 함께하면 이 차이가 분명해집니다. 제가 참여한 프로젝트를 안다고 해서 그 프로젝트의 모든 작업을 제 역할로 써도 되는 것은 아닙니다. 팀이 만든 결과와 제가 직접 수행한 일을 구분해야 합니다. 문장을 자연스럽게 쓰는 것만으로 해결되지 않는 문제였어요.

반면 문체에 관한 피드백은 다른 종류의 정보입니다. 기술을 나열하기보다 선택 이유를 설명해 달라는 요청이나, 반복되는 표현을 피하라는 교정은 이후 작성 방식에 반영할 기준이 됩니다.

이렇게 사용하면서 루나가 참고할 정보를 나누게 됐습니다.

정보 다루는 방식
선호와 반복되는 교정 대화와 작성 기준으로 참고
경험·역할·성과 근거 자료를 찾아 확인
반복 작업 방법 스킬과 워크플로우로 정리
서버·배포 등의 현재 상태 실제 시스템에서 다시 조회

모든 것을 하나의 긴 자기소개에 넣는 방식과는 달랐습니다. 늘 참고할 기준과 필요할 때 찾아야 할 사실, 매번 다시 확인해야 할 상태를 구분하는 일이었습니다.

LLM Wiki에서 나의 온톨로지로

자료를 다시 활용하려면 문서 사이의 관계도 필요했습니다. 프로젝트와 제 역할, 그 과정에서 내린 판단, 판단을 설명할 근거가 연결되어 있어야 했습니다.

예를 들어 ‘핀로그에서 인프라를 담당했다’는 사실은 ‘핀로그의 애플리케이션 코드를 모두 작성했다’는 뜻이 아닙니다. 같은 프로젝트의 문서라는 이유만으로 서로 다른 담당자의 작업을 합치면 잘못된 설명이 됩니다.

그래서 위키와 함께 대상과 관계, 주장과 근거를 구분한 그래프를 운영했습니다. 사람이 읽는 문서는 Obsidian Markdown으로, 구조화된 관계는 JSONL로 관리하고, 검색에는 SQLite 임베딩 인덱스와 Python 도구를 사용했습니다. 검색한 문서에서 관련 관계와 근거를 함께 회수하는 경량 Graph-backed RAG 구조입니다.

설명의 출처관계·주장·근거질문에 맞는 자료Hermes와 도구결과 확인과 교정

제가 말하는 ‘나의 온톨로지’는 저라는 사람을 완벽하게 복제한 모델이 아닙니다. 경험을 어떤 대상으로 나누고, 어떤 관계로 연결하며, 무엇을 근거로 설명할지 정한 구조입니다.

이 구조가 있으면 프로젝트 이름을 찾는 데서 멈추지 않고, 그 경험을 어디까지 제 이야기로 사용할 수 있는지도 확인할 수 있습니다. 다만 관계가 연결돼 있다는 이유만으로 모든 해석이 옳아지는 것은 아닙니다. 원문과 역할 범위는 여전히 검토해야 합니다.

더 많이 기억시키는 것만으로는 부족했습니다

알고수를 운영하면서 AI Agent에게 정보를 계속 누적시키는 것이 오히려 판단을 흐릴 수 있다는 점을 경험했습니다. 개인 지식 저장소에서도 같은 문제를 고려해야 했습니다.

자료를 보존할 필요가 있다고 해서 매번 답변에 등장해야 하는 것은 아닙니다. 지원서에 필요한 경험과 서버 점검에 필요한 설정을 한꺼번에 전달할 이유는 없으니까요.

그래서 우선 참고할 정보와 필요할 때만 찾을 정보, 보관 중심의 정보와 사용하지 않을 정보를 나눴습니다. 새로운 내용을 저장할 때도 기존 내용과 합칠 수 있는지, 요약하거나 대체할 수 있는지부터 살피도록 했습니다.

원본을 보존하는 것과 현재 작업에 정보를 노출하는 것은 다른 문제였습니다. 중요한 것은 루나가 얼마나 많은 자료를 갖고 있느냐보다, 지금 요청에 맞는 맥락을 꺼내 쓰느냐였습니다.

나를 기억하는 것과, 그 기억을 사용하는 것

실제로 쓰다 보면 이 둘이 같지 않다는 것을 알게 됩니다.

이 글을 준비할 때도 루나는 제가 LLM Wiki를 시작한 이유를 다시 물었습니다. 하지만 기존 경험 기록에는 이미 그 계기와 설계 원칙이 남아 있었습니다. 저는 새로 설명하는 대신, 지금까지의 루나를 보면서 글을 써 보자고 했습니다.

기억할 공간이 없는 문제가 아니었습니다. 답하기 전에 기존 기록을 찾아볼지, 사용자에게 다시 물을지를 판단하는 문제였습니다.

반대의 경우도 있습니다. 과거 기록을 찾았다고 해서 현재 상태를 확인한 것처럼 답하면 안 됩니다. 예전에 서버가 정상이었다는 기록은 지금도 정상이라는 근거가 될 수 없습니다. 저장된 지식은 무엇을 확인할지 알려줄 수 있지만, 현재 시스템을 대신하지는 못합니다.

그래서 루나의 작업 방식에는 두 가지가 함께 필요했습니다. 이미 있는 맥락을 먼저 찾아 불필요한 재설명을 줄이는 것, 그리고 기억만으로 답할 수 없는 문제는 실제 원본에서 다시 확인하는 것입니다.

지식 저장소에서 함께 일하는 도구로

LLM Wiki로 시작했지만, 사용하면서 다루는 범위는 기록 정리를 넘어섰습니다. 지금은 Telegram에서 요청을 보내고, 루나가 자료와 도구를 이용해 결과를 만든 뒤 제가 검토하는 방식으로 여러 작업을 이어 가고 있습니다.

그렇다고 모든 판단을 맡기는 것은 아닙니다. 제 경험으로 무엇을 주장할지, 어떤 자료를 공개할지, 만들어진 결과가 의도에 맞는지는 제가 결정해야 합니다. 에이전트의 설명이 자연스러워도 확인을 생략할 수는 없습니다.

돌아보면 Hermes를 사용하며 해 온 일은 프롬프트 하나를 잘 만드는 일보다 넓었습니다. 제 자료를 정리하고, 사실과 선호를 구분하고, 반복되는 작업 방법을 남기고, 잘못된 결과를 고치는 과정이었습니다. 루나는 그 과정에 제가 붙인 이름입니다.

앞으로도 기준은 같습니다. 나에 대해 많이 말할 수 있는 에이전트보다, 필요한 근거를 찾아 실제 작업에 쓰고 모르는 부분은 확인하는 에이전트. LLM Wiki에서 시작한 시도는 그런 도구를 만들어 가는 일로 이어지고 있습니다.
