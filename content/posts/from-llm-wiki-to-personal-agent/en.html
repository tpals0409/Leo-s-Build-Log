It started with an LLM Wiki. After encountering Andrej Karpathy’s LLM Wiki concept, I wanted to organize my project experiences and decisions into knowledge an AI could use by following the evidence.

Project names and technology lists could not fully explain an experience. I needed the reasoning behind decisions, the scope of my responsibilities, and the records supporting those explanations. I began building a personal knowledge store that connected this material so it could be retrieved for later questions.

The tool I introduced to operate that store was Hermes Agent, an AI agent tool that lets a language model read files and carry out work through tools. The personal agent I call Luna is configured around Hermes. I did not train a separate model; I built an environment in which an existing model could consult my materials and working rules.

Changing the execution layer, not rebuilding the knowledge

The store already contained original experience records, wiki pages, and a graph of relationships and evidence before I introduced Hermes. Its workflows used Claude Code commands and a tmux-based execution setup, with Codex connected for review.

Moving to Hermes did not mean recreating these materials or rules. I changed the execution path used to operate the knowledge. Work that depended on calls to multiple CLIs moved into Hermes directly, and review was reorganized as a separate perspective within Hermes.

Role definitions and procedures were connected to Claude Code commands, a tmux setup, and a Codex review path.

Hermes reads role documents and workflows and performs the work directly. It delegates only when independent review or exploration is useful.

I kept the store’s knowledge conventions and role-specific permissions. Changing the meaning of the material while switching tools would also make the migration harder to verify.

One executor does not mean one undifferentiated role

Consolidating execution did not mean granting every task the same authority. Preserving sources, extracting claims, and verifying those claims needed to remain distinct responsibilities.

The preservation role does not arbitrarily reinterpret and rewrite originals. The extraction role leaves weakly supported material as candidates rather than final facts. The review role checks quotations and relationships, while the retrieval role searches and answers with read-only access.

These roles do not all run simultaneously as separate processes. The default is for Hermes to read the relevant role documents and procedures and work through them in sequence. Roles define responsibility and permission more than process counts.

I kept human decisions in the process of merging similar knowledge or resolving conflicting claims. Being able to edit a file should not authorize the agent to decide what my experiences mean.

Connecting natural-language requests to procedures

As part of the migration, I created a skill for the store and a mapping from natural-language requests to workflows. The skill provides instructions about which documents to read and which tools to use.

A request to check the knowledge store’s health maps to an inspection procedure and validation tools. A request to explain an experience with evidence maps to retrieval. Instead of repeating all operating rules for each question, the agent reads the procedure relevant to the request.

Retrieval also goes beyond finding one relevant document. The search result serves as a starting point for checking connected relationships, claims, and evidence. Participating in a project and personally implementing a particular feature are different claims.

This relational structure is what I mean by a personal ontology: not a replica of me, but a definition of how experiences, responsibilities, decisions, and evidence are separated and connected. Hermes was responsible for reading and using that structure through the defined procedures.

A direct path before parallel execution

I configured subagent delegation for independent research and review, but did not make parallel execution the default for every request. Small searches and updates run directly and sequentially in Hermes. Delegation is reserved for work that can be separated.

Multiple agents were prohibited from writing to the same graph file concurrently. A subagent’s completion report was not enough to finish a task: the main agent needed to read and verify its output.

The initial setup also paired a GPT-family main model with Gemini Flash-family delegated models. Parallel smoke tests completed, but a subsequent graph-cleanup task hit a free-tier quota limit and fell back to direct execution. Delegation working once did not establish that it would remain available. The value of retaining the direct path became concrete during actual work.

Showing what is needed, not everything available

While operating AlgoSu, an algorithm study platform, I had experienced how continually adding information to an AI agent could cloud its judgment. I did not want the personal knowledge store to focus solely on remembering more.

For cover-letter writing, one of the early applications, I avoided using the full graph for every task. I separated information to consult first, retrieve on demand, keep mainly for archival purposes, or exclude from use into front / on_demand / archive / off.

This did not mean deleting every experience. Preserving originals and deciding what information to expose for the current writing task were separate concerns. Summarizing, merging, and showing less were part of operating the knowledge store, not just accumulating it.

What I verified during adoption

I did not stop after changing the execution documents. I checked role definitions and workflows for assumptions about the previous tools, and ran graph validation and retrieval smoke tests.

The final inspection at the time found no graph integrity errors, but a warning about a low-confidence relationship remained. Passing structural validation did not establish that every piece of knowledge was true. Checking files and references and judging the meaning of an experience required separate forms of review.

Introducing Hermes was less about completing a personal assistant than establishing an environment that could work with my records. I preserved existing knowledge, moved its execution path, connected roles and verification procedures, and kept the decisions that needed to remain mine.

The interest that began with an LLM Wiki thus grew from how to organize material into how an agent should handle that material. That was also Luna’s starting point.
