시작은 LLM Wiki였습니다. Andrej Karpathy의 LLM Wiki 개념을 보고, 제 프로젝트 경험과 의사결정도 AI가 근거를 따라 활용할 수 있는 지식으로 정리해 보고 싶었습니다.

프로젝트 이름과 기술 목록만으로는 경험을 충분히 설명하기 어려웠습니다. 무엇을 만들었는지뿐 아니라 왜 그렇게 판단했는지, 제 역할은 어디까지였는지, 그 설명을 뒷받침하는 기록이 무엇인지도 필요했어요. 이 내용을 연결해 두고 다음 질문에서도 다시 찾아 쓸 수 있는 개인 지식 저장소를 만들기 시작했습니다.

그 저장소를 운영하는 도구로 도입한 것이 Hermes Agent입니다. 언어 모델이 파일을 읽고 도구를 실행하며 작업할 수 있게 하는 AI 에이전트 도구입니다. 제가 ‘루나’라고 부르는 개인 에이전트도 Hermes를 기반으로 구성한 것입니다. 별도의 모델을 학습시킨 것이 아니라, 기존 모델이 제 자료와 작업 규칙을 참고하도록 환경을 만든 것이죠.

지식을 새로 만드는 대신, 실행 도구를 바꾸기

Hermes를 도입하기 전에도 지식 저장소에는 경험 원문, 위키, 관계와 근거를 담은 그래프가 있었습니다. Claude Code의 명령과 tmux 실행 구성을 사용하고, 검토 과정에는 Codex를 연결한 구조였습니다.

Hermes로 전환하면서 이 자료와 규칙을 처음부터 다시 만들지는 않았습니다. 바꾼 것은 지식을 운영하는 실행 경로였습니다. 기존의 여러 CLI 호출에 의존하던 흐름을 Hermes가 직접 수행하도록 옮기고, 검토도 Hermes 안에서 별도 관점으로 수행하도록 정리했습니다.

Claude Code 명령과 tmux 실행 구성, Codex 검토 경로에 역할과 작업 절차를 연결했습니다.

Hermes가 역할 문서와 워크플로우를 읽고 직접 수행합니다. 독립적인 검토나 탐색이 필요할 때만 하위 에이전트에 위임합니다.

저장소의 지식 규약과 역할별 권한은 유지했습니다. 도구를 바꾸면서 자료의 의미까지 바꾸는 일이 생기면, 전환이 제대로 됐는지 확인하기도 어려워지기 때문입니다.

한 에이전트가 실행해도 역할은 나누기

실행 도구를 하나로 모은다고 모든 작업을 하나의 권한으로 처리하게 하지는 않았습니다. 원본을 보존하는 일, 원본에서 주장을 추출하는 일, 그 주장을 검증하는 일은 구분해야 했습니다.

자료와 출처 유지대상·관계·주장 생성원문과 의미 대조검색 가능한 지식으로 반영

원본을 보존하는 역할은 내용을 임의로 해석해 바꾸지 않습니다. 추출 역할은 근거가 약한 내용을 확정하지 않고 후보로 남깁니다. 검토 역할은 원문 인용과 관계를 확인하고, 검색 역할은 읽기 전용으로 자료를 찾아 답합니다.

이 역할들이 모두 별도 프로세스로 동시에 실행되는 것은 아닙니다. 기본은 Hermes가 필요한 역할 문서와 절차를 읽고 순서대로 처리하는 방식입니다. 역할은 실행 개수보다 책임과 권한의 구분에 가까웠습니다.

의미가 비슷한 지식을 합치거나 서로 충돌하는 주장을 정리하는 일에는 제 판단을 남겼습니다. 에이전트가 파일을 수정할 수 있다는 이유로 경험의 의미까지 임의로 결정하게 하지는 않으려 했습니다.

자연어 요청을 실제 작업 절차에 연결하기

Hermes를 도입하면서 저장소용 스킬과 자연어 요청의 대응표를 만들었습니다. 스킬은 이 저장소에서 어떤 문서를 읽고 어떤 도구를 사용해야 하는지 안내하는 작업 지침입니다.

예를 들어 ‘현재 지식 저장소 상태를 점검해’라는 요청은 점검 절차와 검증 도구로, ‘이 경험을 근거와 함께 설명해’라는 요청은 검색 절차로 연결했습니다. 질문마다 전체 운영 규칙을 다시 설명하는 대신, 요청에 맞는 절차를 읽도록 한 것입니다.

검색도 관련 문서 하나를 찾는 데서 끝내지 않았습니다. 검색 결과를 출발점으로 삼아 연결된 관계와 주장, 근거를 확인하게 했습니다. 프로젝트에 참여했다는 사실과 그 안의 특정 작업을 직접 수행했다는 주장은 구분되어야 하니까요.

이런 관계 구조가 제가 만들려던 ‘나의 온톨로지’에 해당합니다. 저라는 사람을 복제하는 모델이 아니라, 경험과 역할, 판단과 근거를 어떤 대상으로 나누고 연결할지 정한 구조입니다. Hermes에는 그 구조를 읽고 정해진 절차로 활용하는 역할을 맡겼습니다.

병렬 실행보다 먼저 정한 기본 경로

독립적인 자료 탐색이나 검토에는 하위 에이전트 위임을 사용하도록 구성했습니다. 하지만 모든 요청을 병렬로 처리하는 것을 기본값으로 두지는 않았습니다. 작은 검색이나 반영 작업은 Hermes가 직접 순차 수행하고, 서로 분리할 수 있는 작업에만 위임을 사용하도록 했습니다.

같은 그래프 파일을 여러 에이전트가 동시에 수정하는 것은 금지했습니다. 하위 에이전트가 완료했다고 말하는 것만으로 작업을 끝내지 않고, 메인 에이전트가 산출물을 다시 읽고 확인하게 했습니다.

초기에는 GPT 계열 메인 모델과 Gemini Flash 계열 위임 모델을 함께 쓰는 구성도 연결했습니다. 병렬 스모크 테스트는 완료했지만, 이후 그래프 정리 작업에서는 무료 할당량 제한으로 위임이 실패해 직접 수행 경로로 돌아갔습니다. 위임이 가능하다는 것과 계속 사용할 수 있다는 것은 다른 문제였어요. 직접 수행 경로를 기본으로 남긴 이유가 실제 작업에서도 드러났습니다.

자료를 많이 주는 것보다, 필요한 만큼 보여 주기

알고리즘 스터디 플랫폼인 알고수를 운영하면서 AI Agent에게 정보를 계속 누적시키는 것이 오히려 판단을 흐릴 수 있다는 점을 경험했습니다. 개인 지식 저장소에서도 단순히 더 많이 기억시키는 방향으로만 가고 싶지는 않았습니다.

초기 활용처 중 하나였던 자기소개서 작성에서는 전체 그래프를 매번 사용하지 않도록 했습니다. 우선 참고할 정보, 필요할 때 찾을 정보, 보관 중심의 정보, 사용하지 않을 정보를 front / on_demand / archive / off로 나눴습니다.

이것은 경험을 모두 지우는 방식이 아닙니다. 원본을 보존하는 문제와 지금 작성에 어떤 정보를 노출할지 결정하는 문제를 분리한 것입니다. 지식을 쌓는 일뿐 아니라 요약하고, 합치고, 덜 보여 주는 일도 운영의 일부로 보았습니다.

도입하며 확인한 것

전환 뒤에는 실행 문서만 바꾸고 끝내지 않았습니다. 역할 문서와 작업 절차에 이전 도구를 전제로 한 설명이 남아 있는지 대조하고, 그래프 검증과 검색 스모크 테스트도 수행했습니다.

당시 최종 점검에서 그래프 무결성 오류는 없었지만, 낮은 신뢰도의 관계에 대한 경고는 남아 있었습니다. 구조 검증을 통과했다고 모든 지식이 사실로 확정되는 것은 아닙니다. 파일과 참조가 정상인지 확인하는 검사와, 경험의 의미를 검토하는 판단은 따로 필요했습니다.

Hermes를 처음 도입하며 한 일은 완성된 개인 비서를 만드는 것보다, 제 기록을 다룰 수 있는 실행 환경을 마련하는 일에 가까웠습니다. 기존 지식을 보존한 채 실행 경로를 옮기고, 역할과 검증 절차를 연결하며, 제가 결정해야 할 부분을 남겼습니다.

LLM Wiki에서 시작한 관심은 그렇게 ‘자료를 정리하는 방법’에서 ‘에이전트가 내 자료를 어떻게 다뤄야 하는가’로 이어졌습니다. 루나의 출발점도 여기에 있었습니다.
