As the infrastructure owner for PinLog, I worked with information that carried different time horizons. The branch Argo CD deploys from is configuration. A Pod being Ready is a state observed at a particular moment.

Pico needed both kinds of knowledge, but they could not be trusted in the same way. Reading yesterday’s healthy status as today’s can produce a wrong operational decision from an otherwise accurate record.

Contracts and observations have different lifetimes

When reading operational information, it helps to distinguish observations from implementation contracts. Observations are values inspected at a particular moment; contracts describe structures verified in repository configuration and operating documents.

The monitoring workloads were Ready.

This describes their state then. Their health now requires another query.

Argo CD reconciles deployments against main.

This describes the operating structure. Later configuration changes still need checking.

A contract is not timeless either. It simply differs from health data that can change from moment to moment. When reading a search result, the first question was not whether it sounded plausible, but what it described and when.

Source, history, and query data served different purposes

Pico Graph was an internal knowledge store for source- and relationship-based retrieval, not a human-facing Wiki UI. Its data had distinct roles.

store/events.jsonl held canonical knowledge history, while store/current.jsonl was a rebuildable query view. The word current should not be confused with the current operating state. Even an up-to-date knowledge view can contain historical observations.

Preserving sources separately from query results provides a route back to the evidence behind an explanation. But having a source and remaining valid today are different things. Source and time needed to be read together.

Retrieval and mutation had separate permissions

The Pico knowledge tool exposed to Hermes was read-only. Ingestion and mutation were explicit operations in the operating workspace.

Finding an operational fact was therefore not the same operation as changing canonical knowledge. A guess produced while composing an answer could not directly rewrite the operating record through the retrieval tool.

Read-only access did not make every answer accurate, however. Misinterpreting historical material or dropping its date remained possible. Separating write permissions was not a substitute for factual accuracy.

Moving from “was healthy” to “is healthy”

Consider the question, “Is monitoring healthy now?” A historical Ready observation is evidence about the moment it was recorded. Using it directly to answer a question about now skips a necessary check.

Distinguish a question about historical structure from one about current state.

Use recorded structure and evidence to narrow down the systems and fields to query.

Inspect the actual host, Kubernetes, GitHub, or other source system. If inspection is unavailable, disclose that only historical evidence is available.

These steps explain a principle for using the record, not a claim that every question automatically triggered live inspection. Operational knowledge was better used to guide current checks than to eliminate them.

Memory does not replace the server

Looking back at the record, the distinction between roles mattered more than the volume stored. Raw preserved evidence, history recorded knowledge changes, and query data supported retrieval. Current-state answers still required the actual system.

Giving an AI memory helps it recover context. That memory does not replace the server as it exists now. Use memory to find what to inspect, then verify the facts needed for the current decision. That is the principle I want to retain from Pico’s operational knowledge.
