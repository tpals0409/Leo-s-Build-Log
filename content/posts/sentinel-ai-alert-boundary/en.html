When adding AI to incident notifications, I had a question to settle before worrying about good prose: which decisions should AI be allowed to make? Processing an alert into readable text is not the same as notifying an entire channel. Changing a sentence and changing a mention policy carry different consequences.

In PinLog, Sentinel uses Hermes to process alert payloads. But its generated output is not automatically the final message. Trusted code revalidates mentions, URLs, and formatting. This post describes that division of responsibility as recorded in the July 23, 2026 operations snapshot.

An alert explains a situation—and calls for attention

The person receiving an operational alert needs to know what happened, whether it is still happening, and what to do now. That is the reason to turn a payload into something a person can read. A message contains more than an explanation, though. A mention requests someone else's attention, and a URL points them toward the next place to investigate.

I did not want to treat all of those elements as unrestricted text generation. If freedom to rephrase also means freedom to change who gets notified or which message rules apply, operational policy becomes dependent on generated output. Before producing a plausible message for each alert, I wanted the same policy to apply to the same state.

Hermes processes the payload; code owns the final boundary

Alerts originating inside the cluster travel from Prometheus through Alertmanager to the host's Sentinel Receiver, then on to Mattermost. Sentinel uses a dedicated Hermes profile for alerts. The important detail is not the profile's name, but the separate code validation after processing.

Alert originates Alert is forwarded Hermes processing · code revalidation Operational message delivery

Within that flow, Sentinel's responsibilities split as follows. Rather than hiding the AI stage, the design makes explicit where its output meets the operational rules.

Process the alert payload, participating in the preparation of a message for people to read.

Revalidate mentions, URLs, and formatting in the processed output. Generated text is not the authority for the final format.

Compared with using only fixed text, this introduces a stage that must check the processed output. Compared with sending generated output as-is, it gives AI less discretion. I chose to accept that restriction: leave room to process the explanation, without handing over the rules governing an operational message.

Trusted code is not a device that makes every AI explanation true. It establishes a boundary around mentions, links, and the format that goes out. Natural-sounding prose is not, by itself, a reason to consider that boundary satisfied.

Severity and state have explicit policies

The notification policy distinguishes Critical from Warning, and FIRING from RESOLVED. FIRING means the alert is active; RESOLVED means it has cleared. The repeat interval and mention behavior need to be read as separate conditions, not collapsed into a single idea of urgency.

The record specifies one @channel mention and hourly repeats for Critical, and six-hour repeats without mentions for Warning. This summary alone does not establish mention behavior on repeated messages or incident-wide deduplication. What it does establish is that severity determines distinct notification and repeat policies.

A resolution notification matters because an initial alert alone does not tell the reader the incident's current state. The policy avoids leaving someone who saw the warning to guess whether it cleared. Here, “always send” means that resolution is included in the send policy. It is not a guarantee of arrival regardless of the network or the receiving system.

The final line carries three pieces of information

The final line of an operational alert is a one-line summary containing what happened, the current state, and the required action. It is not decoration added to make the message end neatly. It gives the reader a consistent place to find the information they need at the end.

Read what happened alongside the state now. An event's occurrence alone should not imply that it is still ongoing.

Identify what to do after reading the explanation. This distinguishes an actionable summary from one that only describes the situation.

Writing only “what happened” leaves out the current state. Writing only “is it healthy now?” loses the event that led to the message. Including the required action connects the explanation to the reason for reading the alert. AI processing does not change the purpose of that final line.

Controlling format does not establish factual correctness

Looking back, the important part was not simply putting AI in the alert path. It was deciding which responsibilities would stay outside it. Separating payload processing from operational rules turned the broad question “do we trust AI?” into the more concrete question “which parts of its output must code check?”

Still, format correctness and factual correctness are different. Mentions, URLs, and message structure can comply with the rules while the explanation or required action fails to match the real situation. This boundary should not be mistaken for a guarantee of accurate root-cause diagnosis.

The principle I am taking forward is straightforward: let AI process information, but keep responsibility for invoking people's attention and enforcing the final message rules in code. Adding AI to notifications was not just an exercise in delegating more decisions. It also meant deciding which decisions not to delegate.
