It started with an LLM Wiki. After encountering Andrej Karpathy’s LLM Wiki concept, I wanted to organize my project experiences and decisions into knowledge that an AI could use by following the evidence.

Explaining a project takes more than a list of technologies. It also takes the reasons for choosing them, the work I was responsible for, and the problems I encountered. I thought that recording this context would make it reusable in later work.

The tool I used in this process was Hermes Agent. It connects a language model to tools such as file access and command execution, allowing it to carry out work rather than only hold a conversation. I configured a personal agent around Hermes and named it Luna. I did not train a separate model. I built an environment in which an existing model could consult my materials and working rules.

Today, I talk to Luna through Telegram to find information, prepare job applications, and write blog posts. But I did not design its present form all at once. This is a look back at how an experiment that began with an LLM Wiki grew into operating a personal agent.

Turning explanations into reusable records

I wanted to organize more than a list of projects. Even within the same project, different questions call for different information. Describing an architecture, discussing collaboration, and looking back at incident response require different records.

A summary saying “I built this service” was not enough. I needed to be able to trace the reasons for decisions, my role, and the original material supporting an explanation.

I separated original experience records from wiki summaries. The originals preserved the sources, while the wiki presented them in a form I could read and review. If a summary was wrong, I could return to the original.

Hermes handled reading those materials and working with them. Connecting a knowledge store to an agent turned the records from archived material into context for actual tasks.

A name was not a set of working rules

Naming the agent Luna did not make it understand me. What mattered more was deciding what it should consult and which rules should guide its work.

Working on job applications makes this distinction clear. Knowing which projects I participated in does not mean the agent can attribute every task in those projects to me. It needs to distinguish the team’s results from the work I personally did. Fluent writing alone cannot solve that problem.

Feedback about writing style is a different kind of information. Asking for explanations of technical choices rather than technology lists, or correcting repetitive phrasing, provides guidance for future writing.

Through use, I came to distinguish the kinds of information Luna should consult.

Information How it should be handled
Preferences and recurring corrections Guidance for conversation and writing
Experience, responsibilities, and results Facts to verify against source material
Repeated procedures Methods captured in skills and workflows
Current server or deployment state Information to inspect in the actual system

This was different from putting everything into one long introduction about myself. It meant separating standing guidance, facts to retrieve when needed, and state that requires a fresh check.

From an LLM Wiki to a personal ontology

Reusing the material also required relationships between documents. A project, my role, a decision made during the work, and the evidence explaining that decision needed to be connected.

For example, being responsible for infrastructure in PinLog does not mean I wrote all of its application code. Combining different contributors’ work just because the documents belong to the same project produces a false account.

Alongside the wiki, I maintained a graph that distinguished entities, relationships, claims, and evidence. Human-readable documents used Obsidian Markdown; structured relationships used JSONL; retrieval used a SQLite embedding index and Python tools. This is a lightweight Graph-backed RAG structure that retrieves related relationships and evidence along with the documents it finds.

Evidence behind explanationsRelationships, claims, evidenceMaterial relevant to the questionHermes and toolsVerification and corrections

By “my personal ontology,” I do not mean a perfect digital replica of myself. I mean a structure that defines how to divide experiences into entities, connect them, and support explanations with evidence.

That structure lets retrieval go beyond finding a project name to checking which parts of the experience I can claim as my own. But a connection in a graph does not make every interpretation correct. The source and the scope of my responsibility still need review.

More memory was not enough

While operating AlgoSu, I experienced how continually adding information to an AI agent could cloud its judgment. I needed to account for the same problem in my personal knowledge store.

Material worth preserving does not need to appear in every answer. There is no reason to provide application-writing experience and server-check settings together for every task.

I separated information to surface first, information to retrieve on demand, material kept primarily for archival purposes, and information excluded from use. Before storing something new, I also wanted to check whether it could be merged with existing material, summarized, or used to replace an older entry.

Preserving an original and exposing it to the current task are different problems. What mattered was not how much material Luna possessed, but whether it retrieved the right context for the request.

Remembering me and using that memory

In practice, these are not the same thing.

While preparing this article, Luna asked me again why I had started with an LLM Wiki. But that motivation and the design principles were already in my experience records. Rather than explain them again, I asked it to write by looking back at Luna’s history so far.

The problem was not a lack of storage. It was deciding whether to consult the existing records before answering or ask the user again.

The opposite problem also exists. Finding a historical record does not mean the current state has been verified. A record that a server was healthy in the past cannot establish that it is healthy now. Stored knowledge can indicate what to inspect, but cannot replace the current system.

Luna therefore needed both behaviors: consult existing context first to avoid unnecessary repetition, and check the actual source when memory alone cannot answer the question.

From a knowledge store to a working tool

The experiment started with an LLM Wiki, but its scope expanded beyond organizing records. Today, I send requests through Telegram, Luna produces results using materials and tools, and I review them. That is how we work through a range of tasks.

This does not mean handing over every decision. I still decide what to claim about my experience, which materials to publish, and whether a result matches my intent. A natural-sounding explanation is not a reason to skip verification.

Looking back, using Hermes has involved more than crafting a good prompt. It has meant organizing my materials, separating facts from preferences, recording repeatable procedures, and correcting wrong results. Luna is the name I gave to the agent shaped through that process.

The standard going forward remains the same: not an agent that can say a great deal about me, but one that finds relevant evidence, uses it in actual work, and checks what it does not know. The experiment that began with an LLM Wiki has become an ongoing effort to build that tool.
