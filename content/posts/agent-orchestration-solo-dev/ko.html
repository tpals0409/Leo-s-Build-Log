1인 개발에서 12개 AI 에이전트를 오케스트레이션한 방법

알고리즘 스터디를 위한 플랫폼을 만들면서 6개 마이크로서비스를 혼자 개발했어요. 서비스를 오갈 때마다 맥락을 다시 파악해야 했고, 개발 기준을 일관되게 지키기도 어려웠어요. 한 사람의 머릿속에 전체 시스템의 맥락과 기준을 계속 담아두기는 쉽지 않았습니다.

그래서 실제 개발팀의 역할을 AI 에이전트에 나누고, 제가 각 에이전트와 직접 소통하는 대신 Oracle을 단일 창구로 두는 구조를 만들었어요. 처음에는 8개 역할로 시작했고, 이 글에서 다루는 시점에는 12개 역할로 운영했어요. 이후 역할은 더 추가됐지만, 여기서는 12개로 운영하던 시점의 경험을 돌아봅니다.

역할을 나누는 것만으로는 부족했어요

초기에는 Oracle, Conductor, Gatekeeper, Librarian, Architect, Postman, Curator, Herald의 8개 역할을 만들었어요. 각 프롬프트에 역할 설명과 코드 규칙, 보안 원칙을 한꺼번에 넣었죠.

하지만 에이전트를 호출하는 것만으로 협업이 되지는 않았어요. 이전 작업의 결정이 다음 호출에 이어지지 않았고, 작업 순서가 꼬이면 서로 맞지 않는 결과가 나오기도 했어요. 데이터베이스 변경과 API 변경이 독립적으로 진행되면 결과가 충돌할 수 있었죠.

공통 규칙을 각 프롬프트에 따로 복사해 둔 것도 문제였어요. 규칙을 바꿀 때마다 여러 곳을 고쳐야 했고, 에이전트마다 기준도 조금씩 달라졌어요. 문제는 역할 수가 아니라 작업 순서와 경계, 공통 기준을 관리하는 방식이었어요.

공통 규칙을 한곳에서 관리했어요

공통 규칙을 persona-base.md에 모아 단일 기준으로 관리했어요. 코드 컨벤션, 보안 원칙, 보고 방식과 에스컬레이션 경로는 이 파일에 두고, 각 에이전트의 프롬프트에는 역할별 전문 지식만 남겼어요.

공통 규칙을 바꿀 때 한 곳만 수정하면 됐고, 역할별 지시도 더 간결해졌어요. 문서와 결정 기록을 맡는 Scribe, AI 분석을 맡는 Sensei, 디자인 시스템을 맡는 Palette, 사용자 관점에서 결과를 확인하는 Scout를 더해 총 12개 역할로 운영했습니다.

Oracle을 통해 작업을 조율했어요

저는 Oracle과만 대화하고, 에이전트끼리는 직접 소통하지 않도록 했어요. Oracle이 요청을 작업 단위로 나누고 의존 관계를 확인해 각 역할에 전달했어요. 독립적인 작업은 병렬로 실행하고, 다른 작업의 결과가 필요한 일은 순서에 맞춰 진행했어요.

역할별 에이전트는 독립 프로세스로 실행했어요. Oracle은 작업을 배정하고 실행 결과를 수거해 상태를 갱신했고, Watchdog은 타임아웃을 감시했어요. 역할별 잠금으로 같은 에이전트가 중복 실행되는 것도 막았습니다.

에이전트가 자기 역할의 범위 안에서 판단할 수 있는 일은 자율적으로 진행했어요. 반대로 역할 경계를 넘거나 판단이 어려운 문제는 Oracle이 임의로 결정하지 않고 저에게 물어보도록 했어요. AI가 실행을 맡되, 방향과 기준에 대한 최종 판단은 사람이 하는 구조였어요.

작업 순서도 에셜론 방식으로 정리했어요. 인프라와 안전장치를 먼저 준비하고, 기능을 구현한 뒤, UX와 마감 작업을 진행했어요. 의존성이 큰 작업부터 순서를 잡으니 무작정 병렬로 진행할 때 생기던 충돌을 줄일 수 있었어요.

실제 작업에서 확인한 점

스키마 변경을 단계적으로 진행했어요

Problem 서비스의 컬럼 이름을 바로 바꾸려 했을 때, Librarian이 Expand-Contract 방식으로 변경하도록 했어요. Rolling Update 중에는 구버전과 신버전 애플리케이션이 함께 실행될 수 있기 때문이었어요.

새 컬럼을 추가하고 데이터를 옮기면서 애플리케이션을 전환한 뒤, 마지막에 기존 컬럼을 제거했어요. 절차는 늘었지만 서비스 중단 없이 변경을 마칠 수 있었습니다.

인증 변경 뒤 남은 코드를 찾아냈어요

인증을 httpOnly Cookie 방식으로 전환한 뒤에도 localStorage를 사용하는 토큰 코드가 남아 있었어요. Gatekeeper가 이 잔여 코드를 찾아냈고, SSE 연결에서도 쿠키 인증이 적용되는지 확인했어요.

기능을 바꾼 뒤 기존 코드가 모두 정리됐다고 가정하지 않고, 보안 역할이 전체 흐름을 다시 살피도록 한 결과였어요.

결정의 이유를 기록으로 남겼어요

Scribe는 MEMORY.md와 Sprint ADR에 결정과 근거를 남겼어요. 여러 스프린트가 지나도 이전 선택의 이유를 다시 찾을 수 있었어요.

혼자 개발할수록 구현 결과만큼이나 왜 그렇게 결정했는지를 잃지 않는 일이 중요했습니다. 맥락이 사라지면 이미 검토한 대안을 다시 고민하거나 같은 실수를 반복할 수 있으니까요.

회고: 오케스트레이션은 경계와 흐름을 설계하는 일이었어요

에이전트가 많아진다고 자동으로 협업이 잘되는 건 아니었어요. 역할을 분리해도 공통 규칙이 흩어지면 결과가 달라지고, 작업 순서가 없으면 병렬 실행이 충돌을 만들 수 있었어요.

운영하면서 중요했던 기준은 세 가지였어요. 역할의 경계를 정하고, 공통 규칙을 한곳에서 관리하고, 사람의 판단이 필요한 문제를 되돌려 받을 경로를 만드는 것. Oracle은 이 기준 아래에서 에이전트의 작업 흐름과 예외를 관리했어요.

이 구조도 운영 과정에서 계속 바뀌고 있어요. 그래도 12개 역할을 운영하며 분명히 배운 점이 있어요. AI 에이전트 오케스트레이션은 에이전트를 많이 만드는 일이 아니라, AI가 자율적으로 실행할 범위와 사람이 판단할 경계, 작업이 시작되어 결과로 돌아오기까지의 흐름을 설계하는 일이었어요.
