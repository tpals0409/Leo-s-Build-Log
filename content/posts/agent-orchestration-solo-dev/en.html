How I Orchestrated 12 AI Agents as a Solo Developer

I was building an algorithm-study platform on my own, with six microservices to keep in sync. Every time I switched services, I had to reload the context. Keeping development standards consistent across the whole system was difficult too. One person can only hold so much system context in their head.

I started assigning development-team responsibilities to AI agents. Instead of coordinating with each agent directly, I made Oracle the single point of contact. I began with eight roles and expanded the setup to twelve. This post looks back at the system as it existed when I was operating those twelve roles. I added more roles later, but they’re outside the scope of this account.

Splitting roles wasn’t enough

The first eight roles were Oracle, Conductor, Gatekeeper, Librarian, Architect, Postman, Curator, and Herald. I gave each one a prompt containing its responsibilities, coding rules, and security guidelines.

But assigning roles didn’t automatically make the agents collaborate. Decisions from one task didn’t always carry over to the next call, and tasks could run in the wrong order. If a database change and an API change moved ahead independently, their results could conflict.

Copying common rules into every prompt caused another problem. Whenever a shared rule changed, I had to update several prompts. Over time, each agent’s standards began to drift. The problem wasn’t the number of roles. It was how I managed task order, boundaries, and shared rules.

I moved shared rules into one place

I gathered the shared rules in persona-base.md and treated it as the single source of truth. Coding conventions, security principles, reporting expectations, and escalation paths lived there. Individual prompts retained only the knowledge specific to each role.

This made shared rules easier to update and kept role-specific instructions more focused. As I found gaps in the team, I added Scribe for documentation and decision records, Sensei for AI analysis, Palette for the design system, and Scout for user-perspective checks. That brought the setup to twelve roles.

I used Oracle to coordinate the work

I talked only to Oracle; the agents didn’t communicate directly with one another. Oracle broke requests into tasks, considered their dependencies, and assigned them to the relevant roles. Independent tasks could run in parallel, while tasks that depended on earlier results waited their turn.

The role-specific agents ran as independent processes. Oracle assigned work, collected results, and updated task status. A watchdog monitored for timeouts, and per-role locks prevented duplicate runs of the same agent.

Agents could make decisions within their assigned boundaries. When a task crossed those boundaries or required a judgment call, Oracle wasn’t supposed to decide on its own—it brought the question back to me. AI handled execution; I retained the final say on direction and standards.

I also organized work into Echelons. Infrastructure and safeguards came first, feature implementation followed, and UX and polish came last. Ordering work around its dependencies helped reduce the conflicts I’d seen when I tried to parallelize everything.

What I saw in practice

I changed the schema in stages

When I tried to rename a column in the Problem service directly, Librarian steered the change toward the Expand-Contract pattern. During a rolling update, old and new application versions can run at the same time, so an immediate rename can break one of them.

I added a new column, migrated the data while switching the application over, and removed the old column last. It took more steps, but the change was completed without downtime.

I caught leftover code after changing authentication

After switching authentication to httpOnly cookies, some code that used localStorage for tokens was still around. Gatekeeper found the leftover code and checked that SSE connections also used cookie authentication.

That was a useful reminder not to assume that changing the main flow automatically removes every trace of the old one. A security-focused role could review the wider flow against its standards.

I kept the reasons behind decisions

Scribe recorded decisions in MEMORY.md and Sprint ADRs. That made it possible to recover why I’d chosen an approach, even after several sprints had passed.

When you’re building alone, it’s important to preserve not just what you implemented, but why you made that decision. Once the context is gone, it’s easy to revisit the same alternatives or repeat an earlier mistake.

In retrospect, orchestration was about boundaries and flow

Adding more agents didn’t automatically make collaboration work. Without clear role boundaries, responsibilities overlapped. Without shared rules, results varied. And without a defined task order, parallel work could create conflicts instead of saving time.

Three things mattered most: clear role boundaries, one source of truth for shared rules, and a path for bringing decisions back to me. Oracle managed the workflow and exceptions within that structure.

The system continued to change as I used it. But operating twelve roles taught me something that still holds: AI-agent orchestration isn’t about creating as many agents as possible. It’s about designing what the AI can execute autonomously, where human judgment is needed, and how work moves from request to result.
